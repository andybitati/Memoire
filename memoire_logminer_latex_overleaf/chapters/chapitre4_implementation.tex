\chapter{Implementation}

\section{Organisation generale du prototype}
Le prototype \logminer{} est organise autour d'un noyau Python et d'un dashboard web. Les modules principaux sont situes dans le paquet \texttt{src/logminer}. Les scripts experimentaux sont regroupes dans \texttt{scripts}. Les resultats consolides sont exportes vers \texttt{data/processed}, puis transformes en tableaux, figures et captures pour le memoire.

\section{Outils et environnement}
L'implementation repose principalement sur Python pour le pipeline, scikit-learn pour les modeles legers, FastAPI pour l'exposition des services locaux et une interface web pour le dashboard. Les donnees et resultats sont manipules sous forme de fichiers CSV, JSONL et artefacts graphiques. Cette pile technique a ete choisie pour sa simplicite de reproduction, sa disponibilite locale et sa compatibilite avec une experimentation rapide.

\section{Pipeline de traitement}
Le pipeline effectue les etapes suivantes :
\begin{enumerate}
  \item lecture ou decouverte des sources de journaux ;
  \item parsing des formats connus ou conservation en format inconnu ;
  \item normalisation dans un schema commun ;
  \item routage vers une famille de logs ;
  \item detection ou classification ;
  \item correlation des anomalies candidates ;
  \item export CSV et audit.
\end{enumerate}

Le module \texttt{pipeline.py} coordonne la chaine locale. Le module \texttt{api.py} expose les fonctions principales via FastAPI. Les modules \texttt{model\_router.py} et \texttt{model\_compare.py} gerent la selection des familles et la comparaison des modeles.

Dans l'implementation, le pipeline joue un role de glue code scientifique. Il ne s'agit pas seulement d'enchainer des fonctions ; il s'agit de garantir que les fichiers produits restent compatibles avec les experimentations et avec le memoire. Les sorties doivent donc conserver les colonnes attendues, les chemins doivent etre reproductibles et les erreurs doivent etre explicites. Cette contrainte explique le choix de formats simples comme CSV et JSONL pour plusieurs etapes. Ces formats sont moins sophistiques qu'une base specialisee, mais ils facilitent l'inspection, la comparaison et l'archivage des preuves.

Une attention particuliere est portee a la separation entre donnees brutes, donnees traitees et artefacts de redaction. Les donnees brutes volumineuses peuvent rester hors versionnement. Les donnees traitees utiles aux experiences sont exportees dans des dossiers dedies. Les figures et tableaux du memoire sont ensuite generes a partir de ces resultats. Cette organisation reduit le risque de citer une valeur qui ne serait plus liee a une preuve technique.

\section{Parsing multi-format}
Le prototype prend en charge plusieurs formats : CSV, JSONL, syslog, Apache, CloudTrail, HDFS, BGL, Windows XML/EVTX exporte, CEF/LEEF, tcpdump texte et pcap selon les dependances disponibles. Lorsqu'une entree est incomplete ou corrompue, elle est conservee plutot que supprimee. Cette strategie est importante pour l'audit, car une ligne non reconnue peut elle-meme etre un signal utile.

Le parsing est organise autour d'un principe conservateur. Lorsqu'un parseur reconnait un format, il extrait les champs structurants. Lorsqu'il ne reconnait pas completement la ligne, il conserve le message d'origine et produit un statut exploitable. Cette decision est volontaire. Dans une chaine de securite, ignorer silencieusement une entree revient a creer un angle mort. A l'inverse, conserver trop d'informations non structurees peut augmenter le bruit. Le compromis retenu consiste a normaliser ce qui peut l'etre et a garder le reste sous forme de metadonnees.

\section{Registre des modeles}
Les modeles sont stockes dans le dossier \texttt{models}. Le registre documente les familles, types de modeles et volumes associes. Le systeme distingue les modeles supervises, lorsqu'un label est disponible, et les modeles non supervises, lorsqu'il s'agit de signaler des comportements rares.

Le registre evite une ambiguite frequente dans les prototypes de detection : le meme mot ``modele'' peut designer un artefact entraine, une methode algorithmique ou une configuration experimentale. Dans \logminer{}, un modele exploitable doit etre associe a une famille de logs, un type d'apprentissage, un fichier d'artefact, des features attendues et des metriques connues lorsque celles-ci existent. Cette discipline facilite le routage et limite le risque d'appliquer un modele a une source incompatible.

Les artefacts \texttt{joblib} permettent de reutiliser les modeles sans relancer l'entrainement a chaque execution. Cela accelere les tests et rend les demonstrations plus stables. En contrepartie, chaque artefact doit etre documente : dataset d'origine, date de generation, type de features, score de validation et limites connues. Sans cette documentation, un artefact performant peut devenir difficile a interpreter.

\section{Agents intelligents multi-taches}
La version avancee ajoute un runtime d'agents intelligents dans \texttt{agents/intelligent\_runtime.py}. Chaque agent declare ses capacites, conserve une memoire locale des succes, erreurs, durees et decisions recentes, publie un heartbeat enrichi et choisit ses taches selon une politique explicite combinant priorite, confiance, cout, fiabilite observee, urgence, tentatives precedentes et diversite des taches recentes. Les taches supportees couvrent notamment la decouverte de sources, le parsing, le routage de modele, la detection et la correlation.

Deux modes d'execution sont disponibles. Le premier utilise une file locale en memoire pour les demonstrations reproductibles. Le second utilise Redis Streams avec des consumer groups, ce qui permet a plusieurs processus agents de consommer le meme flux de taches. Le worker \texttt{scripts/logminer\_intelligent\_agent\_worker.py} supporte aussi la reprise de taches non acquittees par \texttt{XAUTOCLAIM}, ce qui rend testable un scenario de panne avant acquittement.

Cette implementation donne un sens concret aux termes agents, multi-taches et distribue. Les agents ne sont pas de simples fonctions appelees sequentiellement : ils disposent d'un profil de capacites, d'un etat observable, d'une file de taches et d'une logique de reprise. La distribution reste locale dans les experiences du memoire, mais elle est executee par plusieurs processus independants relies par un bus Redis persistant.

\section{API FastAPI}
La V2 du prototype expose une API locale permettant de lancer des analyses, consulter l'etat des services, interroger les modeles, lire les ressources et recuperer les evenements d'audit. L'API permet aussi au dashboard de fonctionner sans manipuler directement les fichiers internes.

L'API joue un role de separation entre le moteur d'analyse et l'interface. Elle evite que le dashboard depende directement de l'organisation interne des fichiers. Cette separation facilite aussi l'ajout futur de workers, de files d'attente ou de connecteurs vers d'autres plateformes.

\section{Audit et decisions analyste}
Le dashboard permet de valider, rejeter ou reclasser une anomalie candidate. Ces decisions sont enregistrees dans l'audit. Cette fonctionnalite prepare une boucle d'amelioration future, dans laquelle les validations humaines pourraient servir a reduire les faux positifs.

\section{Problemes rencontres}
Plusieurs difficultes ont marque l'implementation. La premiere concerne l'heterogeneite des formats : certaines sources sont tabulaires, d'autres textuelles, et d'autres deja enrichies par un outil externe. La deuxieme concerne l'interpretation des sorties non supervisees : sans labels, un score d'anomalie doit rester une indication et non une conclusion. La troisieme concerne la coherence du dashboard : il faut afficher assez de details pour l'analyse sans transformer l'interface en simple dump technique.

\section{Reproductibilite}
Les experimentations principales sont documentees par des CSV et scripts. Les scripts \texttt{benchmark\_realtime\_workflow.py}, \texttt{run\_resource\_campaign.py}, \texttt{run\_family\_routing\_ablation.py}, \texttt{generate\_memoire\_assets.py} et \texttt{export\_memoire\_figures.py} permettent de regenerer les mesures, figures et tableaux principaux.

\section{Organisation des modules}
Le paquet \texttt{src/logminer} regroupe les composants applicatifs. Le pipeline coordonne les traitements principaux. Le parseur reconnait les formats et produit des objets intermediaires. Le routeur associe les evenements a une famille de logs. Le detecteur applique les modeles disponibles. Le correlateur regroupe les anomalies candidates. L'audit conserve les traces d'execution et les decisions. Cette organisation correspond directement au modele modulaire presente au chapitre precedent.

Le fichier \texttt{model\_compare.py}, ouvert dans l'environnement de developpement, participe a la comparaison des modeles et a la consolidation des resultats. Il s'inscrit dans une logique plus large de registre de modeles : chaque detecteur doit etre associe a une famille, a un type d'apprentissage et a des metriques connues. Cette discipline de nommage et de comparaison evite de melanger des resultats produits dans des contextes differents.

\section{Preparation des donnees}
La preparation des donnees constitue une etape importante de l'implementation. Les journaux doivent etre nettoyes, convertis ou harmonises avant l'application des modeles. Pour les datasets tabulaires, il faut verifier les colonnes, isoler les labels, encoder les variables si necessaire et separer les ensembles d'entrainement et de test. Pour les journaux textuels, il faut extraire les timestamps, messages, sources et severites lorsque ces informations sont presentes.

La preparation n'a pas ete traitee comme une operation invisible. Les scripts conserves dans le dossier de reproductibilite documentent les transformations principales. Cette approche permet de justifier les tableaux et figures du memoire et de relier les valeurs citees aux fichiers qui les ont produites.

\section{Implementation du dashboard}
Le dashboard a ete concu comme une interface de travail. Il regroupe les indicateurs principaux, les resultats, les details d'incident, les ressources, les services et l'audit. Les captures inserees dans le memoire montrent plusieurs vues afin d'eviter de reduire l'interface a une seule image de presentation. La vue d'ensemble montre l'etat global du prototype. La vue resultats donne acces aux anomalies candidates et aux decisions analyste. La vue technique expose les ressources et les services.

L'interet de cette interface est de rendre les sorties du pipeline lisibles. Un fichier CSV peut suffire a un test automatique, mais il ne suffit pas a une analyse humaine. Le dashboard joue donc le role de couche d'interpretation. Il met en forme les evenements et permet de passer d'un signal technique a une decision.

\section{Choix de legerete}
Le prototype privilegie des technologies legeres et accessibles. Python et FastAPI permettent un developpement rapide. Les fichiers CSV et JSONL facilitent l'audit et l'export. Les modeles scikit-learn sont plus simples a entrainer et a deployer localement que des architectures profondes lourdes. Ce choix ne signifie pas que les methodes avancees sont inutiles ; il signifie que le memoire cherche d'abord a valider une chaine complete et reproductible.

\section{Validation fonctionnelle}
La validation fonctionnelle repose sur plusieurs verifications : execution des scripts experimentaux, production des CSV, generation des figures, consultation du dashboard, verification des captures et coherence des tableaux. Cette validation complete l'evaluation quantitative. Elle montre que le prototype ne produit pas seulement des scores, mais aussi des artefacts exploitables pour la redaction et pour l'analyse technique.

\section{Gestion des dependances et portabilite}
La portabilite du prototype depend de la maitrise des dependances. Les dependances principales sont separees des dependances plus lourdes ou optionnelles. Cette organisation permet d'installer rapidement le pipeline de base tout en conservant la possibilite d'ajouter des bibliotheques specialisees pour certains formats ou certaines experiences. Par exemple, la lecture directe de fichiers EVTX peut demander une dependance particuliere, alors que les exports XML Windows restent exploitables avec des outils plus standards.

La portabilite concerne aussi les systemes d'exploitation. Le projet est developpe et teste principalement dans un environnement Windows, mais plusieurs composants Python restent compatibles avec d'autres plateformes. Les scripts PowerShell sont utiles pour la collecte Windows locale, tandis que les scripts Python couvrent le traitement, l'evaluation et la generation d'artefacts. Cette separation permet d'adapter progressivement le prototype a un environnement Linux ou serveur.

\section{Lien entre code et redaction}
Un point important de l'implementation est le lien direct entre code, resultats et manuscrit. Les figures et tableaux ne sont pas seulement dessines manuellement ; ils proviennent de fichiers de donnees et de scripts de generation. Cette pratique reduit les incoherences entre le projet et la redaction. Elle permet aussi de regenerer les assets apres une nouvelle campagne.

Le memoire doit donc etre lu comme un document accompagne d'un depot technique. Les fichiers \texttt{src/logminer} justifient l'architecture, les scripts justifient les experiences, les CSV justifient les valeurs et les captures justifient l'existence du dashboard. Cette relation est un element fort du travail, car elle transforme la redaction en synthese verifiable plutot qu'en description isolee.
