\chapter{Reproductibilité, déploiement et exploitation du prototype}
\label{chap:reproductibilite}

\section{Introduction}

La reproductibilité constitue une exigence importante dans un travail expérimental
combinant traitement de journaux, apprentissage automatique et architecture logicielle.
Un résultat numérique ne possède qu'une valeur limitée s'il n'est plus possible de
déterminer à quelles données, à quel protocole, à quelle configuration et à quel artefact
il correspond.

Dans Ariel \logminer{}, cette exigence est particulièrement importante parce que les
expériences n'étudient pas toutes le même phénomène. Certaines évaluent un classifieur,
d'autres un parser, un routeur, un mécanisme de corrélation, un bus Redis ou encore le
coût d'une architecture multi-agent. Les conditions nécessaires pour reproduire ces
campagnes sont donc différentes.

Ce chapitre rassemble les éléments nécessaires pour reconstruire raisonnablement
l'environnement expérimental et retrouver les preuves associées aux résultats présentés
dans les chapitres précédents. Il décrit l'environnement logiciel, l'organisation des
artefacts, les paramètres importants, les seeds, les données, les modèles, les campagnes
multi-VM et les principales précautions de reproduction.

Le terme \textit{reproductibilité} est utilisé ici dans un sens pragmatique. L'objectif
est de permettre à un lecteur disposant des données et du code de reproduire les protocoles
dans un environnement comparable. Le mémoire ne prétend pas que toute exécution sur
n'importe quelle machine produira une durée ou une consommation de ressources strictement
identique.

\section{Principes de reproductibilité}

\subsection{Reproductibilité du protocole}

Un protocole est considéré comme suffisamment documenté lorsque les informations suivantes
sont disponibles :

\begin{itemize}
    \item dataset ou source ;
    \item règles de prétraitement ;
    \item méthode de séparation ;
    \item caractéristiques utilisées ;
    \item paramètres du modèle ;
    \item seed lorsque nécessaire ;
    \item métriques ;
    \item conditions de sélection du seuil ;
    \item fichiers produits.
\end{itemize}

Cette définition est particulièrement importante pour les campagnes de machine learning.

Deux exécutions utilisant le même algorithme mais des partitions différentes ne constituent
pas nécessairement la même expérience.

\subsection{Reproductibilité logicielle}

La reproductibilité logicielle suppose de connaître :

\begin{itemize}
    \item version de Python ;
    \item dépendances principales ;
    \item organisation du code ;
    \item scripts d'expérimentation ;
    \item emplacement des modèles ;
    \item formats des résultats.
\end{itemize}

Les dépendances qui influencent directement la représentation ou les prédictions doivent
recevoir une attention particulière.

Drain3 en constitue un exemple : un changement de version ou de paramètres peut modifier
les templates produits.

\subsection{Reproductibilité des données}

Une donnée doit pouvoir être identifiée indépendamment de son nom.

Dans ce travail, les manifestes et hashes jouent ce rôle.

Le principe est :

\[
\text{fichier}
\longrightarrow
\mathrm{SHA256}
\longrightarrow
\text{manifest}.
\]

Deux fichiers de même nom mais de hash différent doivent être considérés comme deux copies
distinctes jusqu'à vérification.

\subsection{Reproductibilité des résultats}

Une valeur utilisée dans le mémoire doit idéalement être retrouvable dans un artefact brut
ou agrégé.

La chaîne retenue est :

\[
\text{valeur du mémoire}
\rightarrow
\text{tableau ou figure}
\rightarrow
\text{fichier agrégé}
\rightarrow
\text{résultat brut}
\rightarrow
\text{run}.
\]

Cette structure limite la retranscription manuelle des résultats.

\section{Organisation logique du dépôt}

L'organisation du projet sépare plusieurs catégories de fichiers.

Une structure conceptuelle simplifiée peut être représentée comme suit :

\begin{verbatim}
project/
|
|-- src/
|   `-- logminer/
|
|-- scripts/
|
|-- models/
|
|-- data/
|
|-- experiments/
|
|-- figures/
|
|-- tables/
|
|-- docs/
|
`-- state/
\end{verbatim}

Cette arborescence est illustrative du rôle des dossiers. Le chemin exact peut différer
selon l'emplacement de la copie utilisée.

\subsection{Code applicatif}

Le dossier applicatif contient le noyau du prototype.

On y retrouve notamment les composants responsables :

\begin{itemize}
    \item du pipeline ;
    \item des agents ;
    \item du bus ;
    \item du routeur ;
    \item du superviseur ;
    \item de la mémoire ;
    \item de l'audit.
\end{itemize}

Le code applicatif doit être distingué des scripts utilisés pour produire les campagnes
scientifiques.

\subsection{Scripts expérimentaux}

Les scripts expérimentaux servent à :

\begin{itemize}
    \item construire les partitions ;
    \item entraîner ou charger les modèles ;
    \item exécuter plusieurs seeds ;
    \item calculer les métriques ;
    \item mesurer les ressources ;
    \item consolider les résultats.
\end{itemize}

Cette séparation permet de modifier une campagne sans transformer le fonctionnement
général du prototype.

\subsection{Artefacts de modèles}

Les modèles entraînés sont conservés sous forme d'artefacts sérialisés lorsque cela est
nécessaire.

Leur utilisation doit rester liée à :

\begin{itemize}
    \item la famille de données ;
    \item la configuration ;
    \item les caractéristiques attendues ;
    \item le protocole d'entraînement ;
    \item le hash disponible.
\end{itemize}

Un artefact ne doit pas être réutilisé simplement parce qu'il possède un nom compatible.

\section{Ledger expérimental}

Les campagnes finales utilisent un registre d'exécution append-only.

L'artefact principal est :

\begin{verbatim}
state/EXPERIMENT_LEDGER.csv
\end{verbatim}

Le rôle du ledger est de conserver une trace des campagnes réalisées sans remplacer les
résultats détaillés.

Il peut notamment servir à retrouver :

\begin{itemize}
    \item une phase ;
    \item une campagne ;
    \item un statut ;
    \item un emplacement de sortie ;
    \item certaines informations temporelles.
\end{itemize}

Un ledger append-only limite le risque qu'une ancienne exécution disparaisse lorsqu'une
nouvelle campagne est ajoutée.

\section{Reproductibilité de la comparaison des modèles}

La comparaison utilise cinq candidats :

\begin{itemize}
    \item Random Forest ;
    \item Extra Trees ;
    \item HistGradientBoosting ;
    \item Logistic Regression ;
    \item SGDLogistic.
\end{itemize}

Les cinq scénarios et les cinq seeds produisent :

\[
5\times5\times5=125
\]

exécutions.

Les modèles linéaires utilisent un \texttt{StandardScaler} ajusté exclusivement sur le
train.

Lors d'une reproduction, le scaler doit donc être construit après la séparation entre
train et test.

L'ordre suivant est incorrect :

\begin{enumerate}
    \item scaler sur l'ensemble complet ;
    \item séparation train/test.
\end{enumerate}

L'ordre correct est :

\begin{enumerate}
    \item séparation train/test ;
    \item ajustement du scaler sur train ;
    \item transformation du train ;
    \item transformation du test avec les paramètres du train.
\end{enumerate}

\subsection{Drain3 train-only}

La règle la plus importante pour reproduire cette expérience est la suivante :

\begin{quote}
\textbf{Drain3 ne doit apprendre de nouveaux templates que sur le train.}
\end{quote}

La validation et le test doivent utiliser un mécanisme de matching sans ajout de nouveaux
messages au modèle.

Une reproduction qui autoriserait Drain3 à apprendre sur le test ne reproduirait donc pas
le protocole final du mémoire.

\[

Le seuil est choisi sur validation.

Le critère principal est le F1 maximal.

Les départages utilisent successivement :

\begin{enumerate}
    \item FPR minimal ;
    \item MCC maximal ;
    \item seuil maximal.
\end{enumerate}

Le test reste gelé jusqu'à la sélection finale.

\section{Hashes et intégrité}

\subsection{Pourquoi utiliser SHA-256}

Un hash permet d'identifier précisément un fichier.

Pour un fichier $F$, on considère :

\[
h = \mathrm{SHA256}(F).
\]

Si le contenu du fichier change, son hash change avec une très forte probabilité.

Le hash est donc utile pour :

\begin{itemize}
    \item identifier une copie de dataset ;
    \item vérifier un état Drain3 ;
    \item contrôler un artefact de modèle ;
    \item détecter une modification silencieuse.
\end{itemize}

\subsection{Limite du hash}

Un hash identique prouve que deux contenus binaires sont identiques.

Un hash seul ne prouve pas :

\begin{itemize}
    \item que le dataset est correctement labellisé ;
    \item que la source est scientifiquement représentative ;
    \item que le protocole est correct ;
    \item que le fichier provient réellement de l'institution annoncée.
\end{itemize}

L'intégrité et la provenance sont donc deux propriétés différentes.

\section{Reproduction des statistiques}

\subsection{Campagnes répétées}

Pour les campagnes à $N=5$, les agrégations doivent être calculées sur les cinq valeurs
effectivement obtenues.

La moyenne est :

\[
\bar{x}
=
\frac{1}{5}
\sum_{i=1}^{5}x_i.
\]

L'écart-type échantillonnal utilise le dénominateur :

\[
N-1.
\]

\subsection{Méthodes déterministes}

Lorsqu'une méthode est déterministe et exécutée une fois, le résultat doit rester associé
à :

\[
N=1.
\]

Aucune dispersion artificielle ne doit être générée en dupliquant la même valeur.

\subsection{Intervalles de confiance}

Les intervalles de confiance sont utilisés uniquement lorsque les conditions et données
permettent leur calcul.

Pour une moyenne :

\[
IC_{95}
=
\bar{x}
\pm
t_{0.975,N-1}
\frac{s}{\sqrt{N}}.
\]

Ils restent spécifiques à la variabilité observée dans le protocole.

\section{Ordre recommandé de reproduction}

Une reproduction complète peut suivre l'ordre suivant.

\subsection*{Étape 1 --- Vérifier les données}

Comparer les fichiers disponibles avec le manifeste et les hashes.

\subsection*{Étape 2 --- Recréer l'environnement}

Installer Python et les versions des bibliothèques pertinentes.

\subsection*{Étape 3 --- Reproduire CICIDS}

Exécuter d'abord le contrôle random puis les holdouts.

Cette étape vérifie que la dépendance au split réapparaît.

\subsection*{Étape 4 --- Comparer les cinq modèles}

Utiliser exactement les mêmes scénarios et seeds.

\subsection*{Étape 5 --- Reproduire HDFS/BGL}

Ajuster Drain3 sur le train, geler l'état puis évaluer validation et test.

\subsection*{Étape 6 --- Reproduire le pipeline multiformat}

Mesurer les unités lues, parsées, normalisées et perdues.

\subsection*{Étape 7 --- Reproduire le routeur}

Construire les chunks puis comparer les familles prédites à la vérité fixée.

\subsection*{Étape 8 --- Reproduire le benchmark architecture}

Exécuter les trois modes avec la même charge.

\subsection*{Étape 9 --- Reproduire la corrélation}

Utiliser le corpus de 19 événements et comparer les 120 paires.

\subsection*{Étape 10 --- Reproduire la mise à jour}

Exécuter les trois cas et vérifier les hashes avant/après.

Déployer Redis, lancer les deux workers et vérifier les états du consumer group.

Cet ordre n'est pas obligatoire, mais il sépare progressivement les campagnes locales des

\section{Critères de réussite d'une reproduction}

Une reproduction n'exige pas nécessairement une égalité bit-à-bit de toutes les mesures de
temps.

Les critères dépendent du type d'expérience.

\subsection{Machine learning}

Les métriques doivent être identiques ou cohérentes avec les mêmes seeds et versions.

Une variation significative doit conduire à vérifier :

\begin{itemize}
    \item dataset ;
    \item partitions ;
    \item versions ;
    \item seed ;
    \item prétraitement.
\end{itemize}

\subsection{Performance système}

Les valeurs de durée et ressources peuvent varier selon la machine.

Le résultat le plus important est la structure comparative de la campagne lorsqu'elle est
exécutée sous conditions identiques.

\subsection{Redis}

Les critères portent notamment sur :

\begin{itemize}
    \item nombre d'entrées publiées ;
    \item nombre lu ;
    \item nombre acquitté ;
    \item pending final ;
    \item lag final ;
    \item reprise dans le scénario prévu.
\end{itemize}

\subsection{Corrélation}

Les mêmes groupes doivent conduire à la même classification des 120 paires si les règles et
le corpus sont inchangés.

\section{Causes possibles d'écart lors d'une reproduction}

Plusieurs causes peuvent modifier les résultats.

\subsection{Versions}

Un changement de scikit-learn peut modifier certains comportements internes ou valeurs par
défaut.

\subsection{Ordre des données}

Certaines méthodes sensibles à l'ordre peuvent produire des résultats différents si les
lignes sont réorganisées.

\subsection{Seeds}

Une seed différente modifie les modèles stochastiques.

\subsection{Drain3}

Un changement de paramètres ou l'apprentissage accidentel sur le test modifie les templates
et invalide la comparaison.

\subsection{Machine}

Les mesures CPU, RAM et durée dépendent directement de la machine et de sa charge.

\subsection{Redis}

Une latence différente ou une configuration différente du broker peut modifier les temps
d'exécution et le comportement de claim.

\section{Limites de reproductibilité}

Plusieurs limites subsistent malgré les artefacts disponibles.

Premièrement, certaines informations exactes concernant les versions des systèmes
d'exploitation des VM et la durée réelle bout en bout de certaines campagnes ne sont pas
complètement documentées.

Deuxièmement, les datasets publics peuvent nécessiter une récupération depuis leurs sources
respectives. Leur disponibilité future dépend donc également des institutions qui les
hébergent.

Troisièmement, les performances de temps et de ressources ne peuvent pas être reproduites
à l'identique sur un matériel différent.

Quatrièmement, certains scénarios reposent sur des fichiers locaux ou synthétiques qui
doivent être conservés avec le dossier de preuve si une reproduction exacte est souhaitée.

Cinquièmement, la reproduction d'une interface web dépend également des versions de son
écosystème JavaScript et du navigateur.

Ces limites n'empêchent pas la reproduction méthodologique des expériences principales,
mais elles doivent être connues.

\section{Synthèse du chapitre}

Ce chapitre a décrit les conditions permettant de reproduire les principales expériences
d'Ariel \logminer{}.

L'environnement final repose principalement sur Windows 10, Python 3.11.9 et un ensemble
documenté de versions de bibliothèques. Les expériences stochastiques utilisent des seeds
explicites, tandis que les méthodes déterministes sont signalées comme telles.

Les campagnes CICIDS2017 disposent de protocoles de séparation, d'échantillonnage et de
configuration suffisamment détaillés pour reconstruire la comparaison entre split random
et holdout. La comparaison des cinq modèles conserve les mêmes scénarios et seeds afin de
limiter les variations étrangères au modèle.

Pour HDFS et BGL, l'élément de reproduction le plus important est le gel de Drain3 après
l'entraînement. La validation et le test ne doivent jamais enrichir l'état du parseur.
Les seuils sont sélectionnés sur validation, ce qui maintient le test hors du processus de
réglage.

La validation multiformat, le routeur et le corrélateur disposent chacun d'artefacts bruts
permettant de retrouver les résultats présentés dans le mémoire. La procédure de mise à
jour contrôlée conserve également les décisions et informations d'intégrité nécessaires
pour vérifier la promotion ou le rejet d'un candidat.

Le benchmark monolithe/agents doit être reproduit sur une même machine pour conserver une
comparaison cohérente, tandis que les valeurs absolues de temps et de ressources peuvent
varier selon le matériel.

La validation multi-VM repose sur deux machines virtuelles Linux et un Redis central. Les
runs, streams, consumer groups et contrôles de pending/lag sont suffisamment documentés
pour reconstruire le scénario de laboratoire. Cette reproductibilité ne transforme pas
l'expérience en preuve de haute disponibilité industrielle.

Enfin, les manifestes, hashes et ledger permettent de relier les résultats aux fichiers
et campagnes utilisés. Leur rôle est de réduire l'ambiguïté entre source, copie locale,
artefact et résultat.

Ces éléments complètent la contribution méthodologique du mémoire. Ils permettent de
considérer Ariel \logminer{} non seulement comme un prototype logiciel, mais comme un
prototype expérimental dont les principales observations peuvent être auditées et
reproduites dans un environnement comparable.

La conclusion générale reprend maintenant les objectifs du travail, répond synthétiquement
aux questions de recherche, établit le statut des hypothèses et présente les perspectives
qui découlent directement des limites observées.
