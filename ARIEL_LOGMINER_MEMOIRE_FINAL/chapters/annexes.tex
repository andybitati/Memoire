\section{Rôle de la capture dans le mémoire}

La capture de l'interface complète les preuves quantitatives contenues dans les fichiers
CSV et JSON.

Elle permet de vérifier que les résultats du pipeline peuvent être présentés dans une
interface structurée et qu'un analyste dispose d'un point d'accès aux informations
produites par le prototype.

Elle ne constitue pas :

\begin{itemize}
    \item une mesure de précision ;
    \item une mesure de rappel ;
    \item une étude d'ergonomie ;
    \item une preuve de réduction du temps d'investigation ;
    \item une validation par un SOC opérationnel.
\end{itemize}

Les métriques scientifiques du mémoire restent calculées à partir des artefacts
expérimentaux et non à partir des valeurs affichées dans une capture.

\chapter{Contrat métier des agents}
\label{annexe:agentmessage}

\section{Structure exacte de \texttt{AgentMessage}}

Le contrat métier utilisé par les agents contient exactement sept champs :

\begin{verbatim}
AgentMessage(
    run_id,
    source,
    target,
    message_type,
    payload,
    status,
    timestamp
)
\end{verbatim}

Le tableau~\ref{tab:annexe-agentmessage} précise leur fonction.

\begin{table}[H]
\centering
\caption{Champs du contrat métier \texttt{AgentMessage}}
\label{tab:annexe-agentmessage}
\small
\begin{tabularx}{\textwidth}{p{3.0cm}X}
\toprule
\textbf{Champ} & \textbf{Signification} \\
\midrule

\texttt{run\_id} &
Identifie et corrèle les messages appartenant à une même exécution. \\

\texttt{source} &
Identifie le composant ou l'agent qui émet le message. \\

\texttt{target} &
Identifie le destinataire logique. \\

\texttt{message\_type} &
Décrit le type d'opération ou de résultat transporté. \\

\texttt{payload} &
Contient les informations propres au traitement. \\

\texttt{status} &
Indique l'état métier associé au message. \\

\texttt{timestamp} &
Associe un horodatage au message. \\

\bottomrule
\end{tabularx}
\end{table}

Le contrat ne contient pas directement les champs suivants :

\begin{itemize}
    \item \texttt{event\_id} ;
    \item \texttt{message\_id} ;
    \item \texttt{metadata}.
\end{itemize}

Lorsque des informations supplémentaires sont nécessaires, elles peuvent être transportées
dans le \texttt{payload}.

\section{Séparation entre métier et transport}

Lorsqu'un message est placé dans Redis Streams, Redis génère et manipule ses propres
informations de transport.

Ces informations comprennent notamment :

\begin{itemize}
    \item identifiant de stream ;
    \item consumer group ;
    \item consumer ;
    \item pending ;
    \item ACK ;
    \item claim.
\end{itemize}

L'identifiant de stream ne doit donc pas être confondu avec \texttt{run\_id}.

La relation conceptuelle est :

\[
\boxed{
\text{AgentMessage}
\neq
\text{enveloppe Redis}
}
\]

Cette distinction facilite le remplacement éventuel du mécanisme de transport sans
modifier la structure fondamentale du contrat métier.

\chapter{Règles d'interprétation des résultats}
\label{annexe:regles-interpretation}

Les règles suivantes résument les précautions qui doivent être conservées lors de toute
lecture technique du mémoire.

\begin{enumerate}

    \item Une anomalie non supervisée est une \textbf{anomalie candidate}, pas une attaque
    automatiquement confirmée.

    \item Un F1 élevé sur un split aléatoire ne démontre pas nécessairement la
    généralisation vers un scénario absent de l'entraînement.

    \item Une PR-AUC élevée ne garantit pas un bon F1 au seuil de décision retenu.

    \item Une méthode déterministe exécutée une seule fois doit être présentée avec
    $N=1$, sans variance inventée.

    \item Le résultat HDFS doit tenir compte du fait que la vérité terrain est associée
    aux blocs alors qu'une partie de l'analyse est événementielle.

    \item Le résultat BGL doit être lu avec la forte proportion de templates inconnus dans
    le test.

    \item Une bonne décision de routage ne garantit pas une amélioration de la performance
    prédictive.

    \item La confidence du routeur est une marge heuristique et non une probabilité
    calibrée.

    \item Un ACK Redis n'est pas automatiquement équivalent à la réussite complète de
    toutes les conséquences métier d'une tâche.

    \item Une reprise d'une tâche pending ne démontre pas la haute disponibilité du
    système complet.

    \item Une validation multi-VM de laboratoire ne constitue pas une validation
    multi-site industrielle.

    \item Une capture du dashboard démontre une fonctionnalité visible, pas une amélioration
    ergonomique mesurée.

    \item La mémoire persistante est implémentée, mais son bénéfice causal sur la
    priorisation n'est pas isolé expérimentalement.

    \item La mise à jour contrôlée est fonctionnelle, mais l'apprentissage continu autonome
    reste une perspective.

\end{enumerate}
